既存VPCへのWebポータル同居構成

依頼者向け Web ポータルを、既存 A1 システムと同一 VPC 内に追加する構成の全体像。ドメインは新規取得せず a1-sys.jp を再利用する。公開 API は CloudFront → VPC Origin → 公開ALB（443）、A1Backend からのアカウント発行 API は VPC Lattice 経由の IAM 認証で専用のアカウント発行ALB（443）へ到達する。2026-09-11 決定：ALB・ECSサービスとも公開系とアカウント発行系で完全に分離し、公開側ECSタスクロールからCognitoのユーザー作成・停止・SMS送信の権限を排除した（同一コンテナイメージ・別サービスとして稼働）。デプロイはメンテナンス日を設けて Sorry ページを返す方針（ローリングアップデート）。リソースの詳細な設計値・構築手順・公開前チェックリストは「A1ポータル本番環境設計書」を正とし、本書は全体像とデプロイ方式の設計判断だけを示す。

全体構成

既存 A1 は app.a1-sys.jp（CloudFront→S3）と api.a1-sys.jp（ALB 直）でホスト名が分かれている。ポータルは単一ホスト（事務所別サブドメイン）で、CloudFront が / を S3 に、/api/* を VPC Origin 経由で公開ALBに振り分ける。A1Backend からのアカウント発行・停止 API は、公開経路とは別に VPC Lattice → 専用のアカウント発行ALB（443）を通る。2026-09-11 決定でALB・ECSサービスとも公開系と物理的に分離し、同一ターゲットグループを共有しない構成に改めた。

色は「既存 A1（変更なし）」「構築済み（apply 済み）」「未構築（設計のみ）」の3種。ネットワーク SG・ログバケット・ACM 証明書・Cognito（dev）・SES ドメイン ID（prd）は 2026-09-10 時点で構築済み。ALB・ECS・CloudFront・WAF・VPC Lattice・Custom Email Sender・SNS は未構築。

論点 1

デプロイ方式：メンテナンス枠 ＋ ローリング

決定

メンテナンス日を設けて Sorry ページを返す方針なら、ローリングアップデートで十分。Blue/Green が買うのは「無停止での切替」であり、計画停止を取る前提ではその対価に見合わない。既存 A1 とデプロイ方式が揃うため、CI/CD も 1 系統で済む。

この方針で 公開経路（CloudFront 経由）に限ってはマイグレーションの後方互換制約と、SPA・API のバージョン skew の問題が解消する。Sorry ページの実装自体（CloudFront Function ＋ KVS）は新しい設計対象になる。

⚠️ Sorry ページが遮断するのは公開経路のみ。A1Backend → VPC Lattice → アカウント発行ALB の内部 API はこの CloudFront Function を一切経由しないため、Sorry ページを ON にしても内部 API は稼働し続ける。さらに公開経路自体も事務所 IP は Sorry ページを素通りする設計（メンテ中の疎通確認のため）なので、「メンテナンス枠＝全経路の完全停止」ではない。破壊的マイグレーションを安全に流すには、内部 API の新規受付停止・実行中処理の完了確認が別途必要（下図）。2026-09-11 決定でアカウント発行ECSサービスを独立させたことにより、この停止手順は ECS の desired_count=0 操作という構造的な手段で成立するようになった（旧案の SSM Parameter Store によるアプリ側フラグ実装は不要になった）。旧 SPA を開いたままのブラウザが新 API を呼ぶ互換性の問題は、この方針だけでは解消しない。

ローリングで運用する場合の設定

3件
決定

deployment_minimum_healthy_percent は 100% にする

「Sorry ページで止めている前提なら 0% にして旧新の混在をなくす」案も検討したが、採らない。

0% の利点はメンテ枠では既に得られている。混在区間はそもそも Sorry ページで外から見えない。一方でこれはサービス単位の設定なので、メンテ枠外の緊急ホットフィックスでも全断する副作用だけが残る。100% にして無停止側に倒し、混在が問題になる破壊的変更はメンテ枠で Sorry を出して隠す。

A1Infra/modules/ecs/main.tf:266-267（既存 A1 は 50%）

推奨

deployment_circuit_breaker を有効にする

既存 modules/ecs では未設定。壊れたイメージをデプロイしたとき、有効なら ECS が自動で前のタスク定義へ切り戻す。メンテ枠内で気づける確率は上がるが、自動で戻るに越したことはない。

前提。判定材料は ALB のヘルスチェックなので、/health/ready が DB を見る実装でないとこの機能は働かない（常に healthy と判定されるため、壊れたまま完走する。設計書 §4-6 で対応済み）。

注意

Blue/Green は後から移行できる

ECS ネイティブ B/G はデプロイコントローラが ECS のままで、ローリングから戦略を切り替える形で移行できる。Terraform も aws_ecs_service の deployment_configuration で対応済み（Provider 6.58.0）。

ターゲットグループを最初から 2 本用意しておく必要はない。いま作り込む理由はないが、無停止デプロイが要件化したときの移行先としては現実的。
